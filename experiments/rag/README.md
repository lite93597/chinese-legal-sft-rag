# RAG：索引构建、检索与生成流程

[实验总览](../README.md) · [数据层](../../data/README.md) · [SFT训练](../sft/README.md) · [评测结果](../evaluation/README.md)

本轮RAG使用已有BGE与Qwen3-Reranker模型，没有对它们做新的监督训练。这里的“构建”是整理语料、生成向量、建索引并组织检索增强生成流程。

## 1. 完整资料与检索块

从法条、司法案例和实务卡片形成37,748条完整资料单元，再得到51,017个检索块。语料含 `current/case/practice_card/historical` 四层；保留来源链接、法条编号、版本、日期与父资料ID。

短块用于召回；最终上下文以对应完整资料单元为基础。一个案例的多个块命中后，应按 `article_id` 去重，不把这些块当成互相独立的法律依据。字段和原文例子见[RAG数据示例](../../README.md#rag数据与检索示例)。

## 2. Embedding与FAISS

使用BGE-large-zh-v1.5生成1024维归一化向量，最大Embedding长度512，FAISS内积索引保留51,017个向量。公开 `metadata.json` 的数组顺序与索引位置相同。

可以直接[恢复已有索引](../../README.md#可选直接复用faiss索引)，不必重新编码全部文本。生成向量是Embedding推理，不是对BGE进行训练。添加新语料或更换Embedding模型时，需要建立相应的新索引，不能把不同模型的向量混入旧索引。

## 3. 从用户问题到候选资料

根据用户可见问题分析相关议题，进行法条名称/条号精确定位，以及向量与BM25候选检索、RRF融合，交给Qwen3-Reranker-0.6B进一步排序。不得使用题号、标准答案或旧生成答案决定检索路径。

案件日期和法域用于适用范围处理。相同条号可能属于不同历史版本；`current` 分类或链接存在都不能单独证明本案应当适用该条。材料仅供判断，不会自动完成法律事实认定。

## 4. 原V4上下文组装

本轮上层策略为RAG16，记录在 [config.json](config.json)：

- 最多4个议题、24个候选、6篇完整资料单元。
- 相对无RAG输入的新增上下文预算不超过1,600 Tokens。
- 生成输入上限16,384 Tokens，输出上限4,096 Tokens。
- 资料注入带ID与来源的参考区域，不改变原问题，不将资料中的文本当成新指令。

“6篇完整资料”是数量上限，不意味着每题必须填满6篇。资料过长时按预算选择可完整放入的资料，不能截断长问题、裁掉完整资料后仍宣称原样处理。底层检索器的单次 `candidate_k=20/top_k=5` 与上层4/24/6是不同层级，不应互相替换。

## 5. 接入生成模型与实际运行

RAG条件使用原始模型；SFT+RAG条件使用SFT后的模型，二者使用同一套对应问题的实际RAG输入。Embedding与Reranker本轮实际在GPU上以FP16推理，FAISS在CPU检索；生成模型使用BF16。这是不同模块的分工，不是整个流程都运行在CPU。

仅RAG并不必然提升所有任务。与Base相比，本轮RAG在DISC提升3.9744个百分点，但LawBench、LexEval略降；完整结果见[评测层](../evaluation/README.md)。检索召回、重排与法律答案正确率是不同指标。

## 6. 公开示例与完整工程的区别

首页FAISS代码只演示最小向量召回，不包含完整多议题、版本筛选、重排和生成服务；完整工程源码尚未发布。后续代码放在本目录并引用 `data/rag/`，不能把简化示例冒充原V4全流程。
